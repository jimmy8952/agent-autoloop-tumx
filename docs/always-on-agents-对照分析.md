## 0. 总结

文章给出五个积木：**事件收件箱、定时器、记忆、权限、发件箱**。

| 积木 | 中台实现程度 | 一句话 |
|---|---|---|
| 事件收件箱 | ✅ 完整，部分超出文章 | 事实日志 + 去重 + 事项合并 + 回答接回会话 |
| 定时器 | ✅ 完整 | `later` + cron 共用到期表，到期变事件再进收件箱 |
| 记忆 | ❌ 基本没有 | 连续性几乎全靠续接会话；协议自己写明"没有 Agent 记忆"。建议补上中台自己的三层记忆：事项、规则、本人（第 3 节） |
| 权限 | ⚠️ 一半 | 中台密钥分权很好；但 `askFirst` 只靠提示词，`full` 等于完全放开 |
| 发件箱 | ✅ 正式且克制 | 卡片表 + 投递表 + 去重 + 默认安静；缺噪音评估和节奏控制 |

文章没覆盖、而中台做得很强的部分：可观测性（`why`、`/v1/stream`）、确定性内核与模拟测试、失败处理表、幂等回执重放、`hops` 保险丝、提示注入的结构隔离。

## 1. 文章要点（摘要）

- Agent 不是真的一直开着：大部分时间在睡，被事件叫醒跑**一轮**；一轮在一个**会话**（消息和工具调用的记录）里进行，两轮之间不花 Token。
- **事件收件箱**：持久的事件列表（通常一张表）+ 写入口（HTTP）+ 读取进程；按来源的唯一编号去重；每个收件箱只允许一个活动进程；事件可合并成一轮；用户回复这类后续事件接回原会话，其余开新会话；入口要快速应答，提示注入检查放到一轮里面做。
- **定时器**：两种——Agent 给自己定的跟进、固定周期的任务；单独存储；不直接启动一轮，由调度器找到到期项、更新、往收件箱加一条事件。
- **记忆**：单独存储，映射到数据库或对象存储，要比任何一个工作进程活得久；**只记查不到的**，在别的系统里的只存指针。四类：
  1. 用户的长期指示（单独文件，每轮加载）
  2. 对用户的了解（先一个文件，多了拆小文件、只加载索引）
  3. 已告诉用户的内容（避免重复）
  4. 每个进行中任务的进度文件（做完什么、还剩什么）
  - 示例布局：`instructions.md`、`index.md`、`reported.md` 每轮加载；`notes/`、`progress/` 按需读。
  - **做梦（dreaming）**：可选的后台过程，回看过往会话整理记忆，替换过时条目，发现跨多轮才显现的规律。
  - 上下文：每轮的固定开销（系统提示、工具定义、记忆文件）要精简并用提示缓存；会话太长时压缩或开新会话，两者都会丢细节，所以必须保留的东西要在这一轮里写进记忆。
- **权限**：一轮以用户的权限无人值守地运行，每次工具调用要么执行、要么拦下、要么等批准；凭据放在 Agent 环境外的代理里；auto mode 用分类器审查高风险动作；**延后工具调用**：hook 暂停这次调用、保存会话、给用户看卡片，回答作为收件箱事件回来，开新一轮恢复会话，等待期间可处理别的事件。
- **发件箱**：后台 Agent 交给用户的是结果和要点，不是过程；一轮有三种结束方式：发消息、决定不发、延后调用请求批准；正式发件箱 = 待发消息表 + 分发器；**从安静开始，用评估找打扰的平衡，慢慢赢得注意力**。
- 文章自述没讲或只略讲：可观测性、通用失败处理、工具调用幂等、入门路线、记忆遗忘规则、评估方法、沙箱与多租户。

## 2. 逐项对照

### 2.1 事件收件箱 ✅

| 文章要求 | 中台对应 |
|---|---|
| 持久事件列表 | 只追加的事实日志 + SQLite 投影，可从日志重建 |
| 按来源编号去重 | "来源把同一条事件发了两遍：只记一次" |
| 一个收件箱只一个活动进程 | "同一事项一次一轮"，`group` / `parallel` / `maxActive` 控并发 |
| 合并排队事件 | 同事项排队时新来的事件并进下一轮；`retryLater` 也会把排队的同事项事件并进重试轮 |
| 后续事件接回会话 | 回答、到期复查回到提问/约定时的会话；`resume: true` 让新事件也接上一轮会话 |
| 进程死了能重试 | 租约 + 心跳；5 分钟没报标成"不确定"；重派 |
| 入口快速应答，注入检查放到一轮里 | **更好**：事件文字不进提示词，只进标明"是资料"的文件，且决定不了交给谁、目录、权限（结构隔离而非事后检查） |

小差异：文章提到"一轮进行中又来事件"有三种处理（排到下一轮/并进当前轮/打断重启），中台只做了第一种。目前看是合理取舍，符合"一轮不等人"。（2026-11-20 已定：保持只排到下一轮。）

### 2.2 定时器 ✅

- `later`（跟进，带 `key`，同 key 再写即改时间，可 `cancel`）+ `cron`（周期）。
- cron、later、重试、租约、离线判断共用到期表，外壳只安排下一次到期的定时器。
- 到期后生成事件，进入事项，再派活——与文章"定时器不直接启动一轮"一致。
- 错过的定时醒来只补最近一次。
- 协议里有一条文章没有的经验：要反复等外部恢复时，不要用 `later` 一遍遍接回很长的会话，改写一条 `use: "command"` 的规则定时探测，恢复了才发事件。

### 2.3 记忆 ❌（最大缺口）

`docs/protocol.md` 原文："没有总览页、工作流画布、**Agent 记忆**、模型路由、多租户或插件市场。"

现在每一轮拿到的连续性（`kernel/query.ts` 的 `jobOf`）：

| 字段 | 内容 | 算哪类记忆 |
|---|---|---|
| `session` | 续接的会话 | 会话记录，不是记忆 |
| `context.answers` | 这一轮要接着做的回答，含提问时写的 `about` | 局部的任务进度（只在提问时写） |
| `context.decided` | 这个事项最近 20 个已决定的卡片 | 部分"决定记录" |
| `context.open` | 同来源同组未收尾的卡片 | 部分"已告诉用户" |
| `context.waiting` / `timers` | 未到期/到期的复查及其 `about` | 局部的任务进度 |
| `askFirst` | 全局一个列表 | 长期指示的一小片 |

对照文章四类记忆：

| 文章的类型 | 现状 | 缺口 |
|---|---|---|
| 用户长期指示 | 只有 `askFirst`；其余只能写进每条规则的 `prompt` / Skill | 没有"本人对 Agent 的长期要求"概念 |
| 对用户的了解 | 无 | Agent 学到的偏好、纠正，一轮结束就丢 |
| 已告诉用户的内容 | 只有 `open`（未结案） | `fyi` 通知创建即结案，下一轮看不到；已结案卡片也看不到 → 可能重复说 |
| 任务进度 | 只有 `about`（提问/约复查时才写）+ `resume` | 没有"做到哪、还剩什么"的常设记录 |

**根本问题：连续性主要靠续接会话。** 文章明确说会话太长时压缩或换新都会丢细节，必须保存的东西要写进记忆。协议自己也承认代价："会话很长时，什么都没做的一轮也要花上十几万 Token。"

### 2.4 权限 ⚠️

做得好：
- 密钥分权细：来源、接单程序、每一轮 token、通道、卡片链接、本人各管各的；普通密钥只存 SHA-256。
- 中台密钥不进 Agent 的提示词或资料文件。
- "要问人就结束这一轮、回答变事件、接回原会话、等待期间不占进程"——就是文章的**延后调用**模式，只是粒度在"轮"而不是"单次工具调用"。

不足：
1. **`askFirst` 没有被执行，只被告知。** 全仓库只有 `worker/contract.ts` 把它拼成一句提示词；没有 hook、分类器或任何拦截。Agent 若不照做，直接执行删数据也拦不住。
2. **权限档位太粗：**
   - Claude：`read → plan`，`edit → acceptEdits`，`full → bypassPermissions`（`plugins/claude/agent.ts:10`）
   - Codex：`read-only / workspace-write / danger-full-access`，且 `approval_policy="never"`（`plugins/codex/agent.ts`）
   - `edit` 与 `full` 之间没有"放开但有审查"的中间档。
3. **Agent 用的外部凭据（GitHub、飞书等）在 Agent 自己的环境里**，没有文章说的环境外凭据代理。

### 2.5 发件箱 ✅

- 卡片表（ask / notice，open → decided → done / closed）+ 投递表（version、tries、given_up、first_try_at）+ 通道领卡片 = 文章的"待发消息表 + 分发器"。
- 同 `key` 卡片开着不重发；`tell: always / needed / never`；`fyi`；`resolve` 让后续轮次结案；"注意力最贵，默认安静"。
- 一轮三种结束方式完全对应：done（带 notice）/ nothing / done + ask。

不足：
- **没有噪音评估。** 文章强调用评估找平衡，中台已有全部数据（回答率、多久回答、被直接关掉、"不用决定了"）却没用起来。
- **没有节奏控制。** 无免打扰时段，无把多条 `fyi` 合成每日摘要。

### 2.6 中台超出文章的部分

- 确定性内核：`decide(view, input, now, env)` 只产生事实，不读时钟、随机数、环境、文件；固定种子 20 万步模拟、有界穷举、强杀、变异测试。
- 可观测性：`agent-autoloop why <轮次>`、`/v1/stream`、`runs`、`status` 的用量统计。
- 幂等：领活响应丢了同 `claim` 拿回同一份；回执可重放，内容不同 409。
- 失败处理表：退避 5 分钟 ×2 最长 1 小时、第 3 次告诉你、第 10 次停；接上会话断了不换新会话重做；回执写错只重写回执不重做业务。
- `hops` 8 层保险丝，防止事件互相触发成环。

## 3. 记忆：设计方案（2026-11-20 讨论定稿）

### 3.1 边界：中台只记经过中台的东西

- **中台的记忆**：经过中台的往来——原始事件（用户问了什么）、中台发出的卡片（Agent 问了什么、告诉了什么）、本人的回答、每一轮交回的结论。只存在中台。
- **Agent 的记忆由 Agent 自己解决，与中台无关**：Claude 用 CLAUDE.md 和它自己的 memory；本人为所有 Claude Code 写的 hook（项目目录下关闭时自动保存最近两轮对话，下次 SessionStart 时自动插回）；Codex 用 Codex 自己的办法。
- 这些 Agent 侧的手段可能串（例如同一目录下并行的几个事项），或在 `claude -p` 下不触发。**可以接受**：最坏情况是新会话没有上下文、从头分析一遍，项目自己的 CLAUDE.md 仍然在。

### 3.2 日志、数据、记忆

| | 是什么 | 给谁用 | 中台现状 |
|---|---|---|---|
| **日志** | 发生了什么、谁做的、结果如何 | 给人查账、追溯 | 已有：事实日志（**永久保留，不删除**）、`why`、每轮输出留 14 天 |
| **数据 / 指标** | 可量化的累积：次数、耗时、费用、趋势 | 给人分析 | 部分有：用量统计 |
| **记忆** | 下一轮要用、又查不到的东西 | 给新会话的 Agent | 没有 |

判断标准：**把它删了，下一轮会不会做得更差？** 累积数据只以提炼后的结论（基线）进入记忆。

### 3.3 中台的三层记忆

```
本人层  —— 长期指示（只有本人能改）、对本人的了解        做梦提炼，本人确认
规则层  —— 岗位经验、纠正、基线                          做梦提炼
  ▲ 事项结束后，做梦从这里提炼
事项层  —— 事项记忆：这件事经过中台的全部往来 + 状态      进行中持续记录
(Agent  —— 不由中台管)
```

三层都属于中台，存在中台。

### 3.4 事项记忆

**它存在的唯一作用**：一件事还没做完、却要换新会话时，把前面经过中台的往来交给新会话。另一个用途是事项结束后供做梦提炼上两层。

**内容**——开头是状态，后面是往来：

```
状态：等你回答（卡片 #12：怎么发货）      ← 中台算出
最新进展：已核对库存和地址                  ← 最后一轮的结论
往来记录：事件 → 结论 → 提问 → 回答 → 结论 …
```

- 状态取值：**进行中 / 等你回答（哪张卡片）/ 等复查（几点）/ 已完成 / 搁置**。由中台按未结卡片、待到期复查、`finished` 计算。
- 往来记录包含：事件（来源、类型、对象、一句话）、每一轮的结论（回执第一行）、ask 与 notice 卡片、本人的回答、提问时写给自己的 `about`。
- 记录很长时，只带卡片的标题、选项、回答和每轮结论，正文不带；需要时 Agent 用 `why` 查。

**怎么记**：不是派活时临时从日志拼接，而是一张**持续记录的投影表**，每个事项一行。每次往来（事件归入事项、发卡片、回答、一轮交回结论）由 `evolve` 追加一笔。它和中台其他投影一样，只由 `evolve` 写，可以随时从日志重建；日志本身永久保留。

**生命周期**：

| 状态 | 什么时候 | 会不会注入新会话 |
|---|---|---|
| 进行中 | 事项开始后、结束前 | 会 |
| 已结束 | 满足 3.5 的结束条件 | 不会；保留给做梦提炼 |
| 重新打开 | 已结束的事项又来了新事件 | 恢复成进行中，接着往下记 |
| 搁置 | 空闲超过 20 分钟、Agent 却没声明完成 | 不会；由内核到期判定，不单独发卡片，列在 `status` 和做梦汇总里；再来事件即重新打开 |

### 3.5 什么时候算结束

**两个条件同时满足：**

1. **Agent 明确声明做完了**：回执加字段 `"finished": true`。做事的 Agent 本身就是最了解情况的 AI，不另请子 Agent 判断，省一轮 Token。
2. **中台确认没有尾巴**：没有未结的卡片，没有待到期的复查（`later`）。

注意：**`done` 不等于完成**。协议里 `done` 只表示"这一轮结束了"，Agent 提问时交的也是 `done` 加一张 ask 卡片。

| Agent 声明完成？ | 中台空闲？ | 结果 |
|---|---|---|
| 是 | 是 | 已结束 |
| 是 | 否（还有卡片或复查） | 进行中 |
| 否 | 是 | 进行中；空闲超过 20 分钟转为搁置 |
| 否 | 否 | 进行中 |

**为什么需要搁置**（核对 `kernel/decide.ts`）：中台只在新事件、复查到期、本人回答、`failed` 重试、接单程序失联放开时再派一轮。一轮交回 `done` / `nothing` 后若没有卡片和复查，中台不会再推动这个事项。所以"空闲又没声明完成"的事项会一直挂着，需要搁置来收口。20 分钟是给"没约复查、但外部系统马上会回事件（如 CI 的 webhook）"留的余量。

**每天的定时任务：每天一个独立事项。**
- 定时触发的事件编号本来就是 `规则名@那个时刻`（`tick` 里的 `key`），直接作为当天事项记忆的编号。
- **派活用的事项（lane）不变**，仍是整条规则一个，保证前一天没跑完时第二天不会和它并行。事项记忆的编号和派活的 lane 分开。
- 当天约的复查、提的问题和本人的回答，跟着发起它的那一轮，归到当天的事项记忆。
- 当天声明 `finished` 且无尾巴 → 结束；否则 20 分钟后搁置。第二天是新的一份。

### 3.6 什么时候注入：只在新会话启动时一次

一轮交给 Agent 的东西分两类：

| 每一轮都给 | 只在新会话启动时给一次 |
|---|---|
| 这一轮的新事件、新回答、到期的复查（现在已经在做） | 事项记忆 + 规则层 + 本人层 |

会话还在运行时不再重复注入：第一次已经注入过，之后的往来它都在会话里看到了。

**由接单程序决定注不注入**：中台不知道续接会不会成功，所以每次都把记忆放进 Job，接单程序续接成功就不放进提示词，开了新会话才注入。虚拟机型常驻 Agent 同理，只在它的会话启动时注入一次。

会开新会话的情况（都会用到事项记忆）：

- 规则没写 `resume`（默认），同一事项来了新事件；
- 原会话接不上（会话文件没了、换了接单电脑）；
- 规则换了 Agent（如 Claude 改成 Codex）；
- 上一轮被停掉了；
- 原会话正被另一轮占着；
- `command` 这类没有会话的 Agent；
- 虚拟机型常驻 Agent 崩溃重启；
- 会话太长，主动换新会话。

### 3.7 本人层与规则层：由做梦提炼

**怎么跑**

- 一条定时规则，**每天一次**，凌晨跑（例如 `17 3 * * *`，按 `rules.json` 的时区；错开整点，避开白天派活高峰）。
- `access: "read"`；可单独指定便宜的模型。一次处理所有规则，不按规则拆。
- 中台交给它的资料：**上次做梦以后结束或搁置的事项记忆**、现有规则层与本人层记忆、上次被拒收的条目。
- 没有新结束的事项 → 第一行写"没事可做"，直接结束。

**做什么**

- 规则层：提炼岗位经验、本人给过的纠正、基线；合并重复，替换过时，删除不再用到的。
- 规则层记忆**每条规则一份，不共享**，与 `group` 无关；对几条规则都有用的经验，由做梦分别写进各自的记忆。
- 本人层：对本人（角色、偏好）的了解，**只作提议**。
- 超出上限时由做梦负责合并或删减；中台只负责守上限。

**上限**（中台没有分词器，按字数卡，中文约 1 字 ≈ 1–1.5 token，取保守值）

| 层 | 目标 | 中台按字数卡 | 单条上限 |
|---|---|---|---|
| 本人层（对本人的了解） | ≤ 500 token | 400 字 | 80 字 |
| 每条规则的规则层 | ≤ 1000 token | 800 字 | 100 字 |

- 超出的条目被拒收，写进回执的 `rejected`（与 `resolve` 越界的处理相同），下次做梦会看到。
- **长期指示**（`rules.json`，本人亲自写）不计入以上上限；超过 1000 字时 `check` 提醒，因为每次新会话都要注入。

**本人怎么确认**

- 只有出现本人层提议时才发一张卡片；多数日子不发。
- 卡片正文编号列出提议；选项："全部采纳""都不要"；也可回一句文字，如"采纳 1、3"。
- 7 天没回答，卡片自动关闭，这些提议作废，不再追问。
- 卡片还开着时，新提议先攒着，等它关闭后再发。
- **规则层改动直接生效，不打扰本人**：当天正好要发卡片时顺带列出；平时用 `agent-autoloop memory` 查看。搁置的事项同样：有卡片时顺带列出，平时看 `status`。

**权限**

- **长期指示**写在 `rules.json`，全局一份，每条规则可再加一份，**只有本人能改**。
- 只有标明为做梦的规则，回执才能写记忆（守住"规则才是指令"）；普通轮次不能写上两层。

### 3.8 协议改动草案

回执（普通轮次）新增一个字段：

```jsonc
{ "finished": true }   // 这件事做完了；中台再核对有没有尾巴
```

做梦规则（规则里标明，例如 `"dreams": true`）的回执额外允许：

```jsonc
{
  "memory": [
    { "scope": "rule",  "rule": "处理告警", "key": "网关超时", "text": "超时先查网关，再查服务" },
    { "scope": "rule",  "rule": "处理告警", "key": "旧接口",   "forget": true },
    { "scope": "owner", "key": "小改动", "text": "文案类小改动不用先问" }   // 提议，本人确认后生效
  ]
}
```

`Job` 新增 `memory`，接单程序只在新会话时注入：

```jsonc
"memory": {
  "matter": {
    "key": "[\"意见\",\"#12\",null]", "state": "等你回答", "card": 12,
    "latest": "已核对库存和地址",
    "history": [{ "at", "kind": "event|result|ask|notice|answer|later|…", "text": "…" }],
    "earlier": 0
  },
  "rule":  [{ "key", "text", "at" }],
  "owner": { "instructions": "…", "notes": [{ "key", "text", "at" }] }
}
```

内核侧：

- 新投影表"事项记忆"：`matters`（key、rule、lane、state、finished、latest、entries、opened_at、ended_at、stall_at）和逐行的 `matter_log`，和其他投影一样由 `evolve` 落盘、可从日志重建；
- `finish` 处理里检查结束条件，满足则产生一条结束事实；空闲但没声明完成时，在到期表里登记"20 分钟后搁置"，期间有新往来就撤销；已结束或搁置的事项有新事件归入时，产生重新打开的事实；
- 定时规则的事项记忆以 `规则名@时刻` 为编号，与派活的 lane 分开；
- 规则层、本人层共用一张 `memory` 表（`scope` 区分 rule、owner、proposal、meta），只接受做梦规则的回执和本人确认卡片的回答写入。

### 3.9 必须守住的边界

1. **记忆也是资料，不是指令。** 事项记忆里有别人写的字；上两层由做梦提炼，可能把注入内容保存下来。所以记忆一律标为资料，本人层必须经本人确认，每条带来源轮次，`why` 可查。
2. **长度上限。** 事项记忆超长时只带摘要；上两层有条数和字数上限。
3. **查看与删除。** 提供 `agent-autoloop memory [规则]` 查看，`agent-autoloop forget` 删除规则层、本人层的条目（删除的是投影里的记忆，日志不动）。
4. **兼容性。** 老中台会拒收带不认识字段的整份回执（与当初加 `fyi` 相同）。分开部署时先升中台，或接单程序探测中台版本后再让 Agent 写 `finished`。

## 4. 权限：改进建议

> **现阶段决定（2026-11-20）：不做强制拦截。** 项目处于早期，askFirst 继续只通过提示词约定，相信 Agent 会按约定发卡片询问，不刻意限制它怎么做。以下作为将来出现真实事故时的备选方案保留。

1. **把 `askFirst` 从提示词变成硬约束。** Claude 插件加 PreToolUse hook：命中 askFirst 类动作（删除、重启服务、对外发送、付费调用等，按规则可配）就拒绝执行，并返回"把这件事写进 ask、结束这一轮"。Codex 用同样思路实现。
2. **加一档 `access: "auto"`**，对应 Claude Code 的 auto mode，夹在 `edit` 与 `full` 之间：放开大多数动作，高风险动作由分类器审查。
3. **（远期）凭据代理。** Agent 调外部服务时不持有真实凭据，由环境外的代理补上。成本高，等有真实需求再做。

## 5. 发件箱：改进建议

1. **`agent-autoloop noise`**：按规则统计卡片回答率、平均回答时间、被直接关掉的比例、"不用决定了"的比例；被忽略多的规则建议改成 `tell: never` 或改 Skill。这就是文章说的"用评估找平衡"的最小版本。
2. **节奏控制**：免打扰时段（只压 `fyi` 和非紧急 notice，ask 仍发或延后到时段结束）；多条 `fyi` 合成每日一条摘要。

## 7. 已定与待讨论

已定（2026-11-20 讨论）：

- **中台只记经过中台的往来**（事件、卡片、回答、每轮结论）；Agent 自己的记忆由 Agent 解决（CLAUDE.md、本人的保存/恢复 hook、Codex 自己的办法）。hook 串了或不触发可以接受，最坏是从头分析。
- 记忆存在**中台**，不放在接单电脑或 Agent 上。
- 中台有三层记忆：**事项层、规则层、本人层**，三层都属于中台；不为 Agent 设记忆。
- 日志永久保留，不删除；记忆是从日志派生的投影。
- 事项记忆是**持续记录的投影表**，每次往来追加，不是派活时临时拼接。
- 事项记忆的唯一作用：**事情没做完却换了新会话时，一次性交给新会话**；结束后不再注入，保留给做梦提炼上两层。
- **只在新会话启动时注入一次**，由接单程序判断；每一轮的新事件、新回答照常每轮都给。
- 每轮结论放进事项记忆；记录太长时只带标题、选项、回答和结论。
- 事项记忆开头写清**状态**（进行中 / 等你回答 / 等复查 / 已完成 / 搁置）和最新进展。
- **结束 = Agent 声明 `finished` + 中台没有未结卡片和待到期复查**；`done` 不等于完成；不另请子 Agent 判断。
- 已结束的事项又来新事件 → **重新打开**，接着往下记。
- 本人层、规则层由**做梦**从已结束的事项记忆提炼；本人层需本人确认；长期指示只有本人能改。
- 现有代码不会重派"交回 done、没声明完成"的事项；**空闲超过 20 分钟且没声明完成 → 搁置**，由内核到期判定，不单独发卡片，再来事件即重新打开。
- **定时任务每天一个独立事项**：事项记忆以 `规则名@时刻` 为编号；派活的 lane 仍是整条规则一个，避免两天并行。
- **做梦每天一次**；本人层 ≤ 500 token（按 400 字卡），每条规则的规则层 ≤ 1000 token（按 800 字卡）；超出拒收，由做梦裁剪；本人层提议有才发卡片，7 天不答作废；规则层改动直接生效。
- **现阶段不给 askFirst 加 hook 或其他强制拦截**：只靠派活时提示词里的约定，相信 Agent 会按约定发卡片；等出现真实事故再考虑第 4 节的方案。
- **规则层记忆不共享**：每条规则有自己的一份，与 `group` 无关；通用经验由做梦分别写进相关规则，各自计入上限。
- **一轮进行中来了同一事项的新事件：排到下一轮**（保持现状）。每次只做一件事，先来先做；不并进当前轮，也不打断重来。需要时本人可手动 `cancel`。

### 8.3 和设计稿不同的地方

- 设计稿里事项记忆叫 `thread`，代码里叫 `matter`：中台已有 `threadOf()` 指 `rule + lane`，避免混淆。
- 本人层提议卡片的回答由中台直接处理，不派新的一轮。
- 做梦规则必须是定时规则，整套规则只能有一条：每次做梦读的是"上次做梦以后"结束的事，两条会各看一部分。
- 做梦模板的 `cwd` 指向一个空目录：做梦不需要读文件，而 `~/.agent-autoloop` 里有中台密钥。
- 兼容：老中台不认识 `finished` 和 `memory`，会拒收整份回执，分开部署时先升中台；老中台派的活没有 `memory`，新接单程序照旧工作。升级后中台按格式指纹从日志重建投影，旧数据没有事项记忆，从升级后开始记。
